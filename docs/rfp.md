# RFP — distilled brief & scoring map

This is the condensed version of the Argusoft Hackathon Two brief, plus an explicit map of
**how each design decision earns points**. When a spec is ambiguous, optimize for the
highest-weighted criterion (collaboration/interdependency, 40%).

## The challenge

Build a **Multi-Agent AI System** where specialized agents **collaborate, exchange
information, challenge assumptions, and collectively arrive at a recommendation or action
plan**. The point is *not* a single LLM call — it's demonstrating that multiple specialized
agents solve the problem *better than one*.

Our chosen scenario: **Health Plan Optimizer** (a "completely different domain" is explicitly
allowed by the RFP). It clearly needs multiple perspectives — medical safety, nutrition,
exercise science, and budget — where a single specialist is insufficient.

## Mandatory deliverables

| # | Requirement | Where we satisfy it |
|---|-------------|---------------------|
| 1 | A working multi-agent solution | Full backend + frontend, runnable end-to-end |
| 2 | At least three specialized agents | **Six**: Medical Risk, Nutrition, Fitness, Budget, Critic, Resolver |
| 3 | Agent collaboration & orchestration | LangGraph debate→critic→resolver loop; see [orchestration.md](orchestration.md) |
| 4 | A final recommendation/decision generated by the system | The integrated **Health Plan** produced by the Resolver |
| 5 | An **Agent Trace View** (input/output per agent + how outputs flowed/influenced others) | Live WebSocket-streamed trace UI; see [trace-view.md](trace-view.md) |

The Agent Trace View must show, for each agent: **input received**, **output generated**, and
**how outputs were shared with / influenced other agents**. Our trace event model
(`MESSAGE_SENT`, `CONFLICT_RAISED`, `REVISION_REQUESTED`) makes the *influence* explicit, not
just the I/O.

## Scoring criteria (and how we target each)

| Criterion | Weight | How we win it |
|-----------|:------:|---------------|
| **Agent Collaboration, Orchestration & Interdependency** | **40%** | Agents are *genuinely interdependent*, not parallel silos: Medical Risk gates Nutrition & Fitness; Nutrition and Fitness do a calorie handshake; Budget forces both to revise; the Critic loop sends conflicts back for refinement; the Resolver reconciles. Removing any agent visibly degrades the plan. |
| **Agent Design & Specialization** | **25%** | Six agents with **non-overlapping** expertise and explicit responsibility boundaries (see each spec in [agents/](agents/)). Each contributes something no other agent can. |
| **Solution Quality & Reasoning** | **25%** | Deterministic macro math (no hallucinated numbers), real USDA food data, real prices/web search, medical constraints as hard filters, and a final plan with explicit rationale. |
| **Innovation & Demonstration** | **10%** | Live animated trace view showing the *debate* (conflicts raised, revisions made) — not just a log. Clear "what each agent changed" narrative for the demo. |

## What the judges will ask (prepare answers)

The RFP says teams must be ready to explain these. Short answers below; long-form in the
linked docs.

- **Why were multiple agents required?** A single model can't simultaneously be a safe
  clinician, an accurate macro calculator, a programming-aware trainer, and a budget
  optimizer without conflicts collapsing into vague averages. Specialization + debate
  surfaces and resolves the trade-offs explicitly. (See [architecture.md](architecture.md).)
- **The responsibility & skillset of each agent?** See [agents/](agents/) — one file each.
- **How did one agent's output influence the next step / final recommendation?**
  See the influence edges in [orchestration.md](orchestration.md) and the trace view, which
  renders `MESSAGE_SENT` / `REVISION_REQUESTED` edges between agents.
- **What's lost if an agent is removed?** See the "What is lost if removed" section in each
  agent spec — e.g. remove Medical Risk → unsafe plans; remove Budget → unaffordable plans;
  remove Critic → silent calorie/budget/medical conflicts ship to the user.
- **What was planned vs executed vs extension?** See [build-plan.md](build-plan.md) §status
  and §future extensions.

## "Passing the baton" (extensibility requirement)

The RFP stresses maintainability, modularity, observability, and documentation so a *future
team* can extend the system. We address this with:

- A spec-first repo (this `docs/` tree) so the design is legible without reading all the code.
- A **pluggable agent registry** — adding an agent is a contained change ([contributing.md](contributing.md)).
- Typed message contracts ([data-models.md](data-models.md)) so agents stay decoupled.
- Built-in observability (the trace event stream doubles as an execution log).
